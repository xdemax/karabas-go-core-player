# ТЗ: оптимизация MP3 на текущем VexRiscv

Отдельная задача от `TZ_FAST_MIXER.md`. Здесь только MP3/Helix и его путь до аудио.
Трекерный микшер, релиз и UI не трогаем.

## 1. Текущее состояние

- CPU: **VexRiscv rv32imf**, 75 МГц, **I-кэш 16 КБ**, **D-кэш 8 КБ**, FPU.
- Софт: `rv32imf` / `ilp32f`.
- FPGA: Spartan-6 XC6SLX25; **нет CFU/MAC-ускорителя**.
- MP3: Helix fixed-point + `src/sw/mp3_fpga.c`, скрыт из титульного списка, но
  собирается и выбирается в браузере.
- 128 кбит/с stereo 44.1 кГц уже **не тянет** — слышны пропуски.
- FPU для Helix **не помогает**: декодер fixed-point.
- Ориентир MegaBuzz: NEORV32 70 МГц + **CFU MAC** + 32 КБ локального IMEM;
  без CFU 320 кбит/с не влезает, с CFU — 1.23–1.32 млн тактов на кадр.

## 2. Цель

Получить на текущем CPU устойчивое воспроизведение **128 кбит/с stereo
44.1→48 кГц** с `MIX ≈ 48000`, без underrun. Если получится 192 — хорошо.
320 кбит/с — не обязателен.

Если 128 не получается только оптимизацией C, зафиксировать это цифрами и
предложить аппаратный ускоритель, а не имитировать успех.

## 3. Что профилировать в первую очередь

Сначала — честный профиль текущей сборки, а не переписывание Helix вслепую:

1. `MP3Decode()`: cycles на кадр, cycles на выходной сэмпл.
2. Внутри Helix:
   - `xmp3_PolyphaseStereo` / `xmp3_PolyphaseMono`;
   - `xmp3_IMDCT` / `xmp3_FDCT32`;
   - `xmp3_DecodeHuffman`;
   - `xmp3_Dequantize` / `xmp3_Subband`.
3. `src/sw/helix/assembly.h`: `MULSHIFT32`, `MADD64`, `SAR64` на rv32imf.
4. `src/sw/mp3_fpga.c`: decode loop, ring buffer, resampler, `mixer_write()`.
5. `src/sw/mixer.c` и `analysis.c`: сколько стоит общий выход.

Методика:

- `R_CYCLES` вокруг функций/кадров;
- MP3 128/192/320 кбит/с, stereo и mono;
- считать cycles/кадр, cycles/выходной сэмпл, % CPU при 75 МГц;
- отдельно — худший кадр, не только средний.

## 4. Где искать выигрыш

Разрешено:

- `-O3` для Helix и `-O3`/`-flto` для горячих файлов, если это не ломает
  размер/кэш; проверить `-O2` vs `-O3` vs `-Os` по cycles и I-кэшу;
- убрать лишние `memmove`/`memcpy`/копирования PCM;
- статические буферы (уже есть `HELIX_STATIC`);
- аккуратно переписать hot loops Helix под rv32imf, сохранив бит-в-бит PCM
  на тестовых кадрах;
- оптимизировать ресемплер и запись в FIFO, не меняя качество сильнее
  допустимого;
- проверить, не тратится ли время на `MP3FindSyncWord`, ID3, обработку ошибок;
- при необходимости — отдельный маленький MAC/CFU-ускоритель **как отдельный
  этап** (не в этой же правке C).

Не разрешено:

- менять формат/качество на «mono 24k» без явного согласования;
- трогать трекерный микшер, MOD/XM/S3M/IT;
- менять CPU/FPGA в рамках этой задачи;
- добавлять сторонние чипы;
- скрывать деградацию тестов.

## 5. Критерий приёмки

- 128 кбит/с stereo 44.1→48: `MIX` держится около 48000, `U` не растёт;
- прослушивание без «заиканий» и грубых артефактов;
- профиль до/после с cycles/кадр;
- PCM на тестовом кадре совпадает с эталоном Helix (или отличия объяснены);
- размер кода/данных не выходит за разумный бюджет SRAM;
- если 128 всё равно не проходит — отчёт с цифрами и вариантами:
  CFU/MAC, NEORV32-сопроцессор, ограничение битрейта/моно.

## 6. Что сдать

- профиль текущей сборки;
- патчи Helix/`mp3_fpga.c`/ресемплера;
- тестовый MP3 128 кбит/с и отчёт cycles/CPU;
- отдельный список изменений, чтобы можно было откатить MP3, не задев трекеры;
- без изменений релиза и общего микшера до отдельного решения.
