# Архитектурные решения и рассмотренные варианты

Этот файл фиксирует не только финальное ТЗ, но и варианты, которые уже были
проверены или отклонены. Нужен, чтобы не возвращаться к ним заново.

## 1. Исходный software-движок

Текущий baseline `musicplayer2` включает:

- `src/sw/it/it_parser.c`;
- `src/sw/it/it_player.c`;
- `src/sw/fastmix.c`;
- интеграцию нового IT-движка и MikMod fallback;
- debug-панель с версией сборки, голосами, `%` аудио-сервиса и `r%`.

Профилирование host:

- `it_player_tick` — 3–7%;
- `fastmix` — 93–97%;
- 22-канальные IT могут иметь 39–64 голоса из-за NNA;
- 64-канальный TanDan — 64 голоса, mixer доминирует.

Вывод: оптимизировать tick/эффекты почти бессмысленно; основной резерв —
mixer или аппаратный микшер.

## 2. Software-оптимизации `fastmix`

Рассмотрено:

- **`max_mixed` 32 → 24/16** — даёт +16…+54% на host для 22-канальных файлов,
  но теряет NNA-хвосты. Только как тестовый режим/лимит.
- **Убрать 64-битное деление в `render()`**, когда граница sample/loop не
  пересекается за chunk. Безопасно, но на host даёт лишь ~5% на TanDan.
- **Nearest-neighbor вместо linear interpolation** — +25–30%, но алиасинг;
  только явный performance mode.
- **`FM_CHUNK` 128/256/512**, `-O3` — на host без заметного выигрыша.
- **Сжатие `nv_hi`/active list** — мелкая оптимизация, не решает 22 канала.
- **Master/BG priority** при вытеснении голосов — полезно вместе с лимитом.

## 3. FPU

FPU для IT и аппаратного микшера не нужен:

- IT/`fastmix` — integer;
- Helix MP3 — fixed-point;
- MikMod — integer, но в бинарнике есть dormant float-функции
  `Mix32ToFP_Normal/Stereo`; `DMODE_FLOAT` не включается.

План: отдельно собрать `rv32im`/`ilp32`, проверить `objdump`, убрать/заглушить
неиспользуемые float-пути, сравнить ресурсы. FPU может освободить слайсы, но не
гарантирует fit 64 голосов на Mini G.

## 4. Pre-render IT в PCM/поток

Рассмотрено и отклонено как основной путь:

- 48 кГц stereo 16-bit = 11.52 МБ/мин;
- в 32 МБ SDRAM помещается ~2.5–3 минуты;
- рендер при загрузке идёт тем же CPU; при 22 каналах он может занять минуты;
- `disk_write()` сейчас возвращает `RES_WRPRT`, кэш на SD невозможен;
- теряется интерактивность/позиция/циклы.

Возможен только внешний offline-конвертер в WAV/ADPCM или отдельный поток,
но это не заменяет real-time IT-плеер.

## 5. ESP8266/ESP32

**ESP8266** — не ускоритель: UART 115200, ~11.5 КБ/с; raw stereo 48 кГц —
192 КБ/с, даже MP3 128 кбит/с — 16 КБ/с. Оставить для Wi-Fi/управления.

**ESP32** — потенциально:

- на Mini G есть SPI CS3 и `ESP32_PCM_BCK/RLCK/DAT`; PCM-пины в RTL сейчас не
  используются;
- на Go ESP32 в top не разведён; на Mini пинов нет;
- можно отдать ESP32 MP3-декодирование или весь плеер, но это отдельный проект:
  прошивка, I2S/PCM, синхронизация, протокол, F12;
- для 22-канального IT это не быстрый локальный фикс.

## 6. GUI/спектр

Для нового IT и MP3 `analysis_bands()` не вызывается; спектр там пустой.
Дорогой Goertzel-анализатор работает у MOD/XM/PT3. Отключение GUI для IT даёт
несколько процентов, не решает проблему. Для аппаратного микшера отдельно
решается вопрос low-pass и spectrum tap.

## 7. Аппаратный wavetable-микшер

Выбран как основной путь к 64 голосам.

- универсальный для MOD/XM/IT/S3M (sample-based);
- TDM, 48 кГц, 64 голоса;
- 3–5 DSP48A1;
- состояние в BRAM с double-buffer;
- line cache + SDRAM arbiter;
- CPU остаётся контроллером: tick, NNA, эффекты, UI;
- Go — 64 голоса, Mini G/Mini — сначала 32;
- AY/PT3 и MP3 не входят;
- S3M с AdLib — fallback на MikMod.

Подробности: `HW_MIXER_TZ.md`.

## 8. S3M/MikMod

MOD/XM/IT уже используют `fastmix`. S3M идёт через `VC_WriteBytes()` и сам
микширует внутри MikMod.

Варианты:

- адаптер/экспорт `VINFO` из MikMod;
- нативный S3M-плеер;
- AdLib S3M — всегда fallback.

Подробности: `S3M_INTEGRATION.md`.

## 9. Разделение репозиториев

- `karabas-go-core-player` — релизный `v1.0b`, без экспериментальных ТЗ;
- `musicplayer2` — экспериментальный hardware mixer, этот документ и ТЗ.
