# Профилирование текущего IT-движка и FPU

Это результаты локальных измерений, а не релизные данные. Host-профиль нужен для
относительных выводов: на VexRiscv абсолютные цифры будут другими.

## 1. Где реально уходит время

Host-профайлер, `-O2`, текущий `it_player` + `fastmix`:

| Файл | Каналов | Голосов max/avg | `it_player_tick` | mixer |
|---|---:|---:|---:|---:|
| Keijsig.it | 4 | 4 / 3.5 | ~3% | ~97% |
| chip_summer_2048.it | 22 | 39 / 20.5 | ~3% | ~97% |
| En-trance.it | 22 | 64 / 27.6 | ~3–4% | ~96% |
| GRD_TanDan.it | 64 | 64 / 57 | ~7% | ~93% |

Вывод: `it_player_tick` (эффекты, огибающие, NNA) — не bottleneck. Основное
время — `fastmix`, конкретно `render()`/`kernel()`: на каждый выходной sample
каждого голоса идут интерполяция, две умножки L/R и обновление аккумулятора.

При 64 голосах и 48 кГц это ~3.1M voice-samples/s. В 16-битном non-ramp kernel
примерно 16–20 инструкций на sample; на 75 МГц это уже предел.

## 2. 22 канала — это не 22 голоса

Из-за NNA:

- `chip_summer_2048.it`: 22 канала, до 39 голосов;
- `En-trance.it`: 22 канала, до 64 голосов;
- `GRD_Creek.it`: 17 каналов, до 48 голосов;
- `GRD_TanDan.it`: 64 канала, до 64 голосов.

Поэтому fallback по `used_channels` не отражает реальную нагрузку. Нужен либо
лимит голосов, либо аппаратный микшер.

## 3. Быстрые эксперименты с software mixer

### Ограничение `max_mixed`

Текущий `it_fpga_start()` вызывает `fm_set_max_mixed(32)`.

Host-результаты на 22-канальных файлах (относительные, не target):

| `max_mixed` | chip_summer | En-trance |
|---:|---:|---:|
| 32 | 274x | 267x |
| 24 | 323x (+18%) | 309x (+16%) |
| 16 | 421x (+54%) | 393x (+47%) |

Ограничение 24/16 — это уже потеря NNA-хвостов. Нужно слушать на железе. Как
дешёвый эксперимент — попробовать 24 для тяжёлых IT.

### 64-битное деление в `fastmix render()`

Сейчас на каждый голос/chunk:

```c
cnt = (L - getP(v) + step - 1) / step;
```

Можно сначала проверить, не пересекается ли граница сэмпла/лупа за текущий
chunk, и только потом делить. Это не меняет звук. На TanDan host дал ~5%;
на Keijo — шум. Полезно как безопасная дополнительная оптимизация, но само по
себе 22 канала не спасёт.

### Nearest-neighbor

Замена linear interpolation на nearest даёт +25–30% на host, но появляется
алиасинг. Только как явный performance mode, не по умолчанию.

### Размер chunk

`FM_CHUNK` 128/256/512 на host заметного выигрыша не дал. `-O3` тоже не дал
стабильного выигрыша на host; на RISC-V надо проверять отдельно.

## 4. GUI

Для нового IT и MP3 `analysis_bands()` не вызывается: спектр там и так пустой.
Дорогой Goertzel-анализатор работает у MOD/XM/PT3. Отключение GUI для
22-канального IT даст несколько процентов, не больше. Как основное решение не
рассматривать.

## 5. FPU

Текущая прошивка собрана `rv32imf`/`ilp32f`. В `player.elf` есть FPU-инструкции,
но в основном из MikMod `Mix32ToFP_Normal/Stereo`; при этом `DMODE_FLOAT` в
`src/sw/mikmod_fpga.c` не включается, то есть эти функции не должны вызываться.

Активные IT-пути integer-only:

- `it_player.c` — fixed-point;
- `fastmix.c` — fixed-point;
- Helix MP3 — fixed-point.

Поэтому FPU можно убирать, но только после проверки:

1. собрать CPU `rv32im`;
2. собрать firmware `-march=rv32im -mabi=ilp32`;
3. проверить `objdump` на FPU-инструкции;
4. убрать/заглушить dormant float-пути MikMod;
5. проверить FatFs `ftoa`/double;
6. сравнить LUT/slices/DSP/BRAM/timing.

Это может освободить слайсы, но не гарантирует fit 64-голосного микшера на
Mini G.

## 6. Что из этого следует

1. Дальнейшая оптимизация `it_player_tick` — почти бессмысленна.
2. Реальный путь к 64 голосам — аппаратный микшер.
3. До него можно получить 10–20% безопасными правками `fastmix` и лимитом
   голосов, но это не устранит принципиальное ограничение.
